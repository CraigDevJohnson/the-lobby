# The daily update moves a game the league moved and emails the Member

The daily iCloud update only added (ADR 0015). A game the league moved kept its old time in a Member's iCloud calendar, reminder included, until they pressed **Add N games**. That was one of #103's four choices, built as recommended. The same day, 2026-11-16, Craig asked for the other answer (#105): a moved game moves in the calendar by itself, and the site emails the Member to say what changed.

A game keeps its UID when the league moves it, so the list of UIDs the update kept could not show a move. The site now keeps, beside that list, the start time and field of each game as it last saw them. On each run, a game on the list whose start or field in the soccer backend's answer differs from what was kept has moved. Nothing else counts as a move: not the title, not a score. The site replaces a moved game in the Member's saved calendar with the backend's current one, reminder included, saves the new time and field, and then sends the Member one plain-text email that names each moved game with its old and new day, time and field. The soccer backend is unchanged.

The issue put three choices to Craig, and they are built as it recommended:

1. A moved game is replaced whole, as a press of Add replaces it. Anything the Member changed on that game in iCloud, such as notes or alerts, is replaced.
2. A moved game that is not in the calendar, because the Member deleted it or it sits there under another file name, is left alone, and the email says so.
3. Every Member with the daily update on gets the email. There is no second switch. Craig chose this on 2026-11-19; the first two follow his answers on #103 (ADR 0015).

This changes ADR 0015's "the update only adds" and ADR 0014's "Only Lobby Admin's add sends".

## Considered options

- Reading the event from Apple and changing only its time and field. It keeps the Member's notes, and ADR 0007 and ADR 0015 both chose to spare them: scores are to go in the title, and the update did not rewrite a moved game. But the site would then read a Member's calendar, which it never does, with a password that opens more than calendars. A move is rare, where a score would touch every game, and the email and the switch's hint both say that the Member's own changes are replaced.
- Replacing with no condition, or putting a missing game back at its new time. Either brings back a game the Member deleted on purpose, which ADR 0015 promised stays deleted.
- A second switch for the email alone. The email is how a Member learns that their calendar changed with nobody there, so a move without it is the worse outcome, and one switch is simpler to explain: its hint and Privacy say an email comes with it, and turning the daily update off stops both.
- Giving the email time of its own, as a save has. A save's 3 seconds and an SMTP exchange's 10 after the run's 25 pass the Lambda's 30, and Lambda would then run the whole event twice more.
- Comparing the whole event to spot a change. Its `DTSTAMP` is the time of each request, so every fetch differs.

## Consequences

- The `icloud#<email>` item keeps `written`, the list of UIDs, as it was, and gains `times`: a map from a game's UID to its `start` and `field`. The start is the event's own `DTSTART` as the backend writes it, such as `20261121T191500`, which is already Boise time; the site never converts it, because its Lambda binary carries no time zone data. The field is the first line of the event's description. An item from before has no `times` and reads as it did. The entry is dropped with its UID, cleared with the list when the saved calendar changes, and saved by the same UpdateItem, which now sets three attributes under the same condition (ADR 0015).
- Only games take part. A Session-over notice (`session-over-`) is never compared, never replaced and gets no kept time.
- A new game is added as before, and whether Apple takes it or says it is already there, its start and field are kept with its UID. A game on the list with no kept time, written before this change, has the league's current start and field noted without a call to Apple and without an email. So a game that was already in the calendar at an old time when the update first saw it stays there until the league moves it again or the Member presses Add, and the page does not promise that every game matches the league.
- A moved game is replaced with one request to the address the site stored it at (`<UID>.ics`), carrying `If-Match: *`, so Apple takes it only when the game is still there and the site learns that without reading the calendar. Apple answering 412 or 404 means the game is not there, and the calendar is left alone. Either way the new start and field are kept, so the same move is acted on once. The Member's calendars are listed first, as for a new game, once per Member. A refused password (401) turns the switch off, 429 or 503 stops the run, and any other failure counts as failed and leaves the kept time as it was, so the next day tries again (ADR 0015).
- On a day with no new game and no moved game the run still makes no call to Apple and sends nothing. A run that only notes times, as the first one after this ships does, saves them without a call to Apple.
- The email goes to the Member's sign-in address, never the Apple Account's, from the invite's sender through Fastmail (ADR 0014). It is sent once per Member per run, only when a game moved, and only after the save kept the new times, so a move is never emailed twice. Its subject is fixed, `A soccer game moved`, with no Team name, because headers go out unencoded. The body lists the games moved in the calendar, then the ones not found there and so not changed, each with its old and new day, time and field printed from the kept digits; says that anything changed on a moved game in iCloud was replaced; and says how to stop the emails by turning the daily update off, with the steps to reach the switch, signing in among them: the page shows the switch only to a signed-in Member, after a Team is found and Add to iCloud Calendar is chosen. It names the address of the site it came from, since dev and production both run the update, and carries no calendar link, Member link or Session link.
- `internal/app` builds the SMTP sender once and hands it to Lobby Admin and to Let's Plan Soccer. Unless both `SMTP_PARAMETERS` and `INVITE_FROM` are set, games still move and no email is sent. A send that fails is logged by its stage and reply code alone and is not tried again. The sender's errors now start `email:`, not `invite email:`.
- The run still stops at 25 seconds. The email is sent inside that time, so a Member's moves are not started with less than 12 seconds left: their moved games wait for the next day with their kept times unchanged, and nothing is lost. New games are added regardless. A move saved without its email would never be emailed.
- The closing log line keeps its counts and gains `moved`, `missing` (moved games not found in the calendar) and `emailed`. Log lines still carry counts and errors only: never a Member's address, a UID, a title or a link.
- Members who already had the daily update on get the email without a new choice. They turned it on under a hint that said a moved game keeps its old time, and a Privacy page that said the invite was the only email.
- Left as they are, on purpose. A press of Add does not record what it wrote, so after a move the Member applied by pressing Add, the next run replaces the game again and emails about it. A game that leaves the backend's answer and later returns at a new time is treated as new, so it keeps its old time in the calendar. A game the league cancels stays in the calendar. Google Calendar and the Member link get no email; a subscribed calendar moves the game by itself. An email that did not send is not sent again. A move is read from two things the soccer backend writes, the digits of an event's `DTSTART` and the first line of its description, so a change in that repository to the form of either would read as every game moving, each one replaced and all of them listed in an email; such a change needs the kept times in mind.
- Dev and production each run the update and each can send, so a Member with the switch on in both gets two emails for one move, each naming its own site. The dev switch stays off except while proving (ADR 0015).
- No infra change: the rule, the permissions and the SMTP settings were there already. The rule's description in `infra/modules/site/schedule.tf` still says only that the update adds games, because changing it would be a change to AWS.
- Not proved against a real Apple Account. #103's proof on dev, on 2026-11-16, covered adding only. Prove on dev first: what Apple answers to `If-Match: *` for a game that is there and for one that was deleted, that the Member's devices show the new time, that the reminder lands at the new time, and that the email arrives.
- The switch's hint says that a moved game is moved and an email follows, that the Member's own changes to it are replaced, and that a deleted game stays deleted. Privacy names the second email, counts each game's time and field among what is kept, and says that turning the daily update off stops the emails.
- aws-setup's `aws-design.md` §6.4 follows: the third field on the `icloud#` item, and the scheduled run reading the SMTP login and sending through Fastmail (that repository, separate change).
