# The daily iCloud update runs in the site

Add to iCloud Calendar wrote games only when a Member pressed **Add N games** (ADR 0012). Games the league posted later, and next Session's games, didn't arrive until the Member came back and pressed again, where a Member link picks them up by itself. On 2026-11-16 Craig asked for the same on iCloud (#103): once a day, find the games of a Member's Teams that aren't in their calendar yet, and add them. This is the daily update that ADR 0007 and `CONTEXT.md` said would come later, for iCloud only.

The update runs in the site, because the site holds the Member's app-specific password and the soccer backend must never see it (ADR 0012). One EventBridge rule in each environment, `site-<env>-icloud-daily`, invokes the site Lambda's `live` alias once a day with the constant input `{"task": "icloud-daily"}`. `cmd/site` tells that event from an HTTP request, and answers an event it doesn't know with an error, where it used to answer 403, which looked like a success. The rule's clock is UTC and it runs at 16:00, which is 9 or 10 in the morning in Boise, because a shared calendar may tell its other people about each game added.

For each Member who has turned the daily update on, still holds the `soccer` grant and has Remembered teams, the site makes the same `POST /feeds` call the Member link makes and keeps the Teams the backend moved on in the same way (ADR 0011), so the update follows Remembered teams from Session to Session as ADR 0007 planned. It then asks the backend's `POST /calendar` for those Team IDs with `since` set to now, which answers only the games that haven't started, and adds the ones it hasn't added before. The soccer backend is unchanged.

The issue put four choices to Craig, and they are built as it recommended: a game deleted from iCloud stays deleted, a game the league moves keeps its old time until the Member presses Add, each Member turns the update on for themselves, and a Member with no Remembered teams is told to add Teams to My calendar first. The same day Craig asked for the other answer to the second, as a follow-up (#105): a moved game moves by itself and the Member is emailed. Until that is built the update only adds. Changed by ADR 0017 (2026-11-19): that is built. A game the league moves is replaced in the calendar and the Member is emailed, and the item also keeps each game's start and field, so what follows about only adding no longer holds for a moved game.

## Considered options

- EventBridge Scheduler, which ADR 0002 named for this. A schedule needs a role to invoke the Lambda, and the deploy role may pass roles only to Lambda. A rule needs only an invoke permission on the function, and Minecraft's idle stop uses a rule too.
- Running it in the soccer backend, where `docs/infrastructure.md` drew the scheduler. The backend would need the Member's password, which ADR 0012 keeps from it.
- Bringing a deleted game back the next day. It needs no list of what was written, but the run would ask Apple about every upcoming game every day.
- Rewriting a game the league moved. That wipes the Member's own notes on the game.
- On for everyone connected. Existing connections were made under "only when you press Add".
- Turning the switch on adds the Teams on the page to My calendar, for a Member with no Remembered teams. The card says to add them first instead.

## Consequences

- The update only adds. The `icloud#<email>` item gains the switch and the list of UIDs the update has put in the saved calendar or found already there. A game not on the list is stored with a create-only request (`If-None-Match: *`) and nothing else. Whether Apple creates it or answers that it is already there (412), its UID goes on the list and it is never written again. So the update never rewrites a game and a Member's own changes stay, a game they deleted after that stays deleted, and a game the league moves keeps its old time in iCloud, reminder included, until the Member presses Add, which still rewrites the games it is given. On a day with nothing new the site makes no call to Apple.
- The list starts empty, so the first run after a Member turns the update on asks Apple about every upcoming game once, and a game deleted before then comes back that once. The list is cleared when the saved calendar changes, and a new connection starts with an empty list and the switch off. Turning the switch off keeps the list, so turning it on again doesn't bring back a game the Member deleted. Game UIDs the Member's feed no longer holds are dropped from it, so it stays small; a notice's UID is kept, because the backend can leave a notice out for a day.
- When a Team can't be followed, the feed's Session-over notice is added too, as the baseline promises for the Connected calendar. It is told apart by its UID (`session-over-`, where a game's starts `game-`) and added whatever its day. The update takes nothing out of a calendar, so unlike the Member link's notice it stays after the Team moves on.
- The switch is on the connected iCloud card, off by default (`POST /api/soccer/icloud/daily`, which makes no call to Apple; `GET /api/soccer/icloud` answers `"daily": true` while it is on). It is opt in because existing connections were made under "only when you press Add", and the password, which opens more than calendars, is now used with nobody there. The page and Privacy say so. The card won't turn it on for a Member with no Remembered teams, and a run skips a Member who has none.
- Turning the switch on saves the calendar showing in the picker, and the update writes only to that calendar. On a day with something new it lists the Member's calendars first, as a press does, and skips a Member whose saved calendar Apple no longer lists. The card shows that Member's switch as off, and turning it on saves the calendar then showing. It adds every upcoming game of the Remembered teams, whatever is checked on the page, and with the Member link also in Apple Calendar each game shows twice. The card says both.
- When the league is down or the backend isn't answering, the whole run stops and tomorrow's run tries again; the soccer backend's own alarm already emails Craig. When Apple says to slow down (429 or 503), the whole run stops too, since the limit may not be per account. When Apple refuses a password (401), that Member's switch is turned off and nothing else changes; the page's own check on their next visit drops the refused password and says so, as before. Any other failure with Apple skips that Member or that game, and the next day tries again. Nothing is retried within a run.
- Lambda runs a failed or timed-out scheduled run two more times, so a run must end by itself and succeed. It stops at 25 seconds, inside the Lambda's 30, saves each Member's list as it goes, and ends by logging counts. Members are taken one at a time and games one at a time. Members a run doesn't reach are reached on a later day, because Members already up to date cost no call to Apple, so a first run, or the morning after a Session's games are posted, may take more than one morning.
- The site lists its iCloud connections with a Scan filtered by kind, as Lobby Admin lists Members (ADR 0013), and saves the switch and the list with an UpdateItem that sets those two alone, and only while the item still holds the password and calendar the run read, with the switch still on. So a run can't bring back the password of a Member who disconnected meanwhile, put an old list on a new connection or calendar, or turn back on a switch the Member turned off while it ran. The site role already had both actions on its table, so it needs nothing new, and ADR 0011's "GetItem, PutItem and DeleteItem only" now reads with UpdateItem added as well as Scan. Changed on 2026-11-20 (#131): the item also carries a connection ID, made anew each time the Member connects, and the save's condition names it beside the password and the calendar. The Scan is eventually consistent and a run takes time, so the run reads the Member's item again, with a strongly consistent GetItem, before it lists their calendars and before each game it sends to Apple. A Member who disconnected, connected again, picked another calendar or turned the switch off meanwhile gets nothing more written. The switch and a press of Add now save with conditional UpdateItems of their own, which change only the connection they read. When another of the Member's requests saved the calendar or the switch first, they read the item again and try on what is kept, at most three tries in all, before answering 409 `icloud_conflict`; a connection that is gone or was made again answers `icloud_not_connected`.
- The rule, its target and the invoke permission are in `infra/modules/site`. The deploy roles' `events:` actions on rules named `site-<env>-*` are in `infra/bootstrap`, which Craig applies by hand before the rule merges, because a merge applies dev by itself. Dev and production each run the update, so a Member connected in both gets two runs, and the dev switch stays off except while proving.
- The run's log lines carry counts and errors only: never a Member's address, an Apple Account, a calendar address, a UID or a link.
- Not proved against a real Apple Account. ADR 0012's list still stands, and what this design assumes about Apple comes from Apple's support pages and CalDAV client projects, not from a test of ours: Apple publishes no rate limits, and one project that asks iCloud a lot reports 429s and then a 401 on everything for a while, hence the few calls, no retries and stopping on a 429; and the create-only request is reported to answer 412 when the game is there, under the same file name or, from an imported file, under another. Prove on dev first: the 412 on a game already there, a deleted game staying deleted, the reminder and Boise time landing, and what Apple answers for a game already imported from a file.
- Left out on purpose: Google Calendar, which the same run could cover later, scores, and any alarm or metric on the site, which has none yet.
- aws-setup's `aws-design.md` gains the rule, the two new fields on the `icloud#` item and the second use of Scan (that repository, separate change).
