# the-lobby

[![CI](https://github.com/CraigDevJohnson/the-lobby/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/CraigDevJohnson/the-lobby/actions/workflows/ci.yml) [![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

The site behind [craigdevjohnson.com](https://craigdevjohnson.com): a personal front page for the Tools Craig builds for family and friends, with sign-in for the people he invites. Each Tool's backend lives in its own repo; this one holds the site itself.

Run `task` to list the commands. The screens (the public welcome, The VIP Lobby, Privacy, Let's Plan Soccer at `/soccer`, the Minecraft Launcher at `/minecraft`, Foundry at `/foundry` and Lobby Admin at `/lobby/admin`) are a React app in [web/](web/), built by `task ui:build` into `internal/web/dist`, where the Go server embeds them; `task run` builds them first. Building them needs Node 20.19 or later; `task ui:test` needs Node 22.18 or later.

The Let's Plan Soccer screen is here; its league access and calendar files are the [soccer](https://github.com/CraigDevJohnson/soccer) backend's (ADR 0001). The site forwards `/api/soccer/*` and the public Session link address `/soccer/link/{token}.ics` to the address in `SOCCER_BACKEND_URL`, signing each request outside a developer's computer (ADR 0006). `SOCCER_BACKEND_SIGNING` overrides that when set: `lambda` signs even locally, to try the deployed backend from a developer's computer with AWS credentials and a region, and `off` never signs. With `task run` it defaults to `http://127.0.0.1:8081`, where the soccer repo's own `task run` listens. When the backend cannot be reached the page says so; nothing is simulated. A Member with the `soccer` grant also gets My calendar: Remembered teams under `/api/soccer/me`, kept in the site's own table, and a secret Member link at `/soccer/link/member/{secret}.ics` that the site builds through the backend's `POST /feeds` (ADR 0011). With sign-in disabled on a developer's computer, My calendar answers `401 signed_out`. The same Members also get Add to Google Calendar (ADR 0007): the site connects their Google account at `/soccer/google/connect` and `/soccer/google/callback`, keeps that access encrypted in its table, and on each press of Add writes the games the backend's `POST /events` builds into the calendar they pick (`/api/soccer/google`, `/api/soccer/google/add`, `/api/soccer/google/disconnect`). It reads the Google client's ID and secret and the token key from the SecureStrings `client-id`, `client-secret` and `token-key` under the Parameter Store path in `GOOGLE_PARAMETERS` (`/the-lobby/<env>/google/` when deployed); unset, the page doesn't offer it. They also get Add to iCloud Calendar (ADR 0012): the Member gives the site their Apple Account email and an app-specific password, which the site keeps encrypted with the same token key, and on each press of Add it stores the games in the backend's `POST /calendar` file in the iCloud calendar they pick, over CalDAV (`/api/soccer/icloud`, `/api/soccer/icloud/connect`, `/api/soccer/icloud/add`, `/api/soccer/icloud/disconnect`). It is offered wherever `GOOGLE_PARAMETERS` is set. `infra/google/wizard.sh`, run on Craig's Mac, walks through the Google Cloud side for dev and production and saves those settings. The code is public under the MIT licence; it is not taking contributions.

The Minecraft Launcher's page and access check are here; each world's status, and starting and stopping it, belong to the [minecraft](https://github.com/CraigDevJohnson/minecraft) repo's launcher backend. [docs/minecraft-backend.md](docs/minecraft-backend.md) is the contract the site calls at `MINECRAFT_BACKEND_URL` (signed like the soccer backend, overridden by `MINECRAFT_BACKEND_SIGNING`). Until it is set, the page says no server is set up for the Launcher. Minecraft Admin at `/minecraft/admin` switches each world's mods on or off through the same backend; it needs the `minecraft-admin` grant, which the Launcher's routes don't accept, just as the Launcher's `minecraft` grant doesn't reach the mods.

Foundry's access check is here. The player page at `/foundry` is the-lobby #24, showing the status and the way in; Foundry Admin at `/foundry/admin` starts and stops the server; the Foundry server's status, and starting and stopping it, belong to the [foundry](https://github.com/CraigDevJohnson/foundry) repo's controller. [docs/foundry-backend.md](docs/foundry-backend.md) is the contract the site calls at `FOUNDRY_BACKEND_URL` (signed like the soccer backend, overridden by `FOUNDRY_BACKEND_SIGNING`) for `/api/foundry/server`, which needs the `foundry` or `foundry-admin` grant, and for `/api/foundry/admin/server`, `/api/foundry/server/start` and `/api/foundry/server/stop`, which need `foundry-admin`; a stop also needs the Member's confirmation that nobody is playing. Until it is set, a Member with either grant is told Foundry has no server configured. `FOUNDRY_JOIN_URL`, Foundry's join page, is given to a Member with either grant when the status can't be checked. The foundry repo's `task run` serves the controller locally for `curl`; the site's route can't reach it there, because sign-in is disabled on a developer's computer and it answers `401 signed_out`.

Lobby Admin at `/lobby/admin` is the Owner's screen for Members, for anyone with the `lobby-admin` grant (ADR 0013). It lists this environment's Members with their Tools, when each was last here and on how many devices, and changes them through `/api/lobby/members` (`GET`) and its `POST` routes `/add`, `/remove`, `/grant` and `/sign-out`, which write the site's own table. Every route needs `lobby-admin`, and a change needs a same-origin JSON request. The page won't remove its user or take away their own `lobby-admin`; `site member add` grants it in the first place. Adding a Member there is the whole invite: Access emails a sign-in code to any address and the site lets in only addresses with a Member record (see [Inviting Members](infra/README.md#inviting-members)). When Lobby Admin adds a Member, the site also emails them their invite from `The Lobby <lobby@craigdevjohnson.com>` through Fastmail's SMTP server (ADR 0014): how to sign in at that environment's `SITE_BASE_URL`, their Tools with links, each Minecraft world's addresses read from the Launcher's backend (or a link to `/minecraft` when they can't be read) and how to join Foundry. The SMTP login is read from the SecureStrings `username` and `password` under `SMTP_PARAMETERS` (`/the-lobby/<env>/smtp/`); unless both `SMTP_PARAMETERS` and `INVITE_FROM` are set, as with `task run`, nothing is sent. The add's answer carries `"invite": "sent"` or `"failed"`, a failed send never undoes the add, and the page still shows the line to copy. Grant changes and `site member add` send nothing. For someone who also holds `minecraft-admin`, the page offers to put a new or newly granted Minecraft Launcher Member's player on the allowlist through `POST /api/minecraft/admin/players`, the route Minecraft Admin's Players card uses; the site stores no player name, so taking a player off stays on Minecraft Admin. A Site card reads `GET /api/lobby/status`, behind the same grant: the environment, the commit the running build came from (go build's VCS stamp, so empty under `go run`), whether Google and iCloud calendars are offered (`GOOGLE_PARAMETERS` set), and whether each Tool's backend is set up and answered one signed check just now (Let's Plan Soccer's and Foundry's `GET /healthz`, the Launcher's `GET /server`, naming no Member, all at once within 6 seconds). Nothing is kept between checks.

The family devices page at `/admin` serves the two configuration profiles for the family's devices, rendered by `internal/profile` from `KIDS_DOH_URL`, `ADULTS_DOH_URL` and `GATEWAY_ROOT_CA_PEM`, the outputs of `infra/zero-trust` (ADR 0009). It sits behind its own Cloudflare Access application for the two adults and never looks at the Sign-in session (ADR 0010). `site profile kids|adult` writes the same files on a computer. Until the settings are set, the page says the profiles are not configured yet.
